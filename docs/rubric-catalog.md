# Каталог рубрик v1

Backend #99 переносит исходный каталог: три набора, 15 критериев, 75 описаний уровней. Каталог хранится в `src/data/assessment/rubrics.v1.json` как неизменяемый ресурс пакета. Коды и тексты сверяются с исходной транскрипцией тестом SHA256; уровни API упорядочены от 1 до 5.

| Категория оценивания | Критерии | Версия | Максимум исходных баллов |
| --- | --- | --- | --- |
| `product` | P1–P5 | 1 | 25 |
| `technical_integration` | T1–T5 | 1 | 25 |
| `research` | R1–R5 | 1 | 25 |

`max_raw_score` — сумма пяти максимальных значений критериев. Это не взвешенная итоговая оценка экзамена.

## Чтение

Оба запроса требуют действующий Bearer-токен существующей системы авторизации:

```http
GET /v1/assessment/rubrics
Authorization: Bearer <access_token>

GET /v1/assessment/rubrics/research/versions/1
Authorization: Bearer <access_token>
```

Первый запрос возвращает массив в порядке product, technical_integration, research. Второй — один набор. У набора поля `assessment_kind`, `name`, `version`, `max_raw_score`, `criteria`; у критерия — `code`, `name`, `description`, `levels`; у уровня — `score` и `description` с исходным объяснением.

Без авторизации — 401. Неизвестная категория или положительная отсутствующая версия — 404. Нечисловая версия, ноль или отрицательное значение — 422. Публичных POST/PUT/PATCH/DELETE для каталога нет. Справочник общий для всех авторизованных пользователей и не содержит оценок или данных пространств.

## Привязка существующего типа проекта

Тип процесса («Курсовой проект» и его этапы) сохраняет прежнее назначение. Поле `assessment_kind` явно выбирает одну из трёх категорий оценивания:

```http
PUT /v1/project-types/42?workspace_id=7
Authorization: Bearer <access_token>
Content-Type: application/json

{"assessment_kind":"research"}
```

Также поле принимается при `POST /v1/project-types/` и возвращается в create/update/get/list типах. Нужны прежние права `workspace:update` и разрешение сервиса на управление типом в соответствующем пространстве. Неизвестный код отклоняется схемой (422), в БД действует CHECK `ck_project_type_assessment_kind`.

Пропуск поля при обновлении сохраняет текущую категорию; `{"assessment_kind":null}` снимает привязку. Старые записи и новые типы без явно выбранной категории имеют `null`. По названию категория не угадывается. При копировании системного шаблона в пространство категория сохраняется.

Миграция `a99b10c11d12` добавляет nullable String(32) и CHECK. Идентификаторы, имена и этапы существующих типов не меняются. Downgrade удаляет только новое поле и ограничение, поэтому введённые категории при откате теряются.

## Версии и следующие задачи

В #99 доступен только начальный каталог v1. Его нельзя перезаписывать при изменении критериев. Черновики, публикация, хранение новых редакций и выбор опубликованной версии относятся к #100; экземпляры Exam — к #101. Эти функции API ещё не предоставляет. Выбранная реализация #99 не означает утверждения всей S0 #93 командой.

## Техническая приёмка

| Требование #99 | Результат | Доказательство |
| --- | --- | --- |
| Набор однозначно соответствует типу; 15 критериев и 75 уровней совпадают с каталогом | PASS | Явная nullable-категория; тесты CRUD/копирования и прав; canonical SHA256 `39bb7db9c64617ade5a7524c5d9c3014844e56d529fe465bdb5388da575ad063` проверяет все исходные тексты и коды |
| Пять значений 5 дают 25/25 | PASS | Для всех трёх наборов проверены пять максимумов 5 и их сумма 25 |
| API отдаёт уровни 1–5 с объяснениями | PASS | ASGI-тесты реального роутера сверяют все объяснения и порядок, list/detail, версию и ошибки |

Проверки каталога, связи и HTTP: `pytest tests/unit/test_rubric_catalog.py tests/unit/test_project_type_rubric_mapping.py tests/unit/test_stage_service.py tests/unit/test_rubric_api.py --no-cov`.

Проверка миграции: `pytest tests/integration/test_rubric_mapping_db.py --no-cov`. Нужна переменная `RUBRIC_TEST_DATABASE_URL` с доступом CREATE DATABASE к временной PostgreSQL. Тест создаёт свою отдельную БД со случайным именем, выполняет upgrade/check/downgrade/upgrade, проверяет NULL старых строк и отказ CHECK для неизвестного кода, затем удаляет только созданную БД. Без явной переменной тест пропускается. Локально проверено на PostgreSQL 14.17; в CI тест выполняется на PostgreSQL 18.

Проверка пакета: сборка wheel, установка в чистое окружение и вызов `load_catalog()` вне репозитория возвращают три набора. Окончательные результаты полного pytest и CI приведены в PR.

Ревью второго backend-разработчика и общий записанный мини-экзамен E08-T03 (frontend #82) учитываются отдельно; технические тесты не заменяют эти пункты DoD.
